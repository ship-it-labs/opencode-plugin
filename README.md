# OpenCode Plugin

Exposes the Ship-It platform's build, runtime, artifact, filesystem, network and usage capabilities to the AI as OpenCode tools. The plugin is the only interface the AI uses, and it authenticates with a single account API key.

## Install

Install from npm and restart OpenCode:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "plugin": ["opencode-shipit-runtime"],
}
```

```bash
npm install -g opencode-shipit-runtime
```

Then give the plugin your account key. Create one in the website dashboard
under API keys, and write it to `~/.config/opencode/shipit.key`:

```bash
echo "ox_live_xxxxxxxxxxxxxxxxx" > ~/.config/opencode/shipit.key
```

The plugin reads the key from `SHIPIT_API_KEY` first and falls back to that
file, because launchers do not always forward custom environment variables to
plugins. The key is only ever shown in full at creation time, so copy it then.

Set `SHIPIT_CONTROL_PLANE_URL` if your control plane is not on
`http://localhost:3000`.

## Tools

### Project

| Tool | Purpose |
| --- | --- |
| `project_upload` | Archive the project and upload it so it can be built |

`project_upload` is the first step of any build. It walks the project directory,
skips dependency caches and build output, writes a ZIP, and uploads it. The
archive is checksummed server-side, and the build workflow re-verifies the
checksum before extracting.

`exclude_dirs` replaces the default exclusion list, so pass every name you still
want excluded if you supply it. The defaults cover `node_modules`, `dist`,
`build`, `out`, `.next`, `.turbo`, `.cache`, `coverage`, `target`, `venv` and
similar. Build output is deliberately excluded: it is regenerated by
`build_commands` on the runner, so uploading it wastes upload time and often
contains absolute paths from another machine that would break the build.

### Build

| Tool | Purpose |
| --- | --- |
| `build_submit` | Submit install/build/test commands to GitHub Actions |
| `build_status` | Poll build status and exit code |
| `build_logs` | Read stdout and stderr from a build |
| `build_list` | List recent builds |

### Runtime

| Tool | Purpose |
| --- | --- |
| `runtime_start` | Start a sandboxed runtime session |
| `runtime_stop` | Stop a runtime and destroy its filesystem |
| `runtime_restart` | Restart a runtime in place |
| `runtime_status` | Status, app URL, lease expiry |
| `runtime_list` | Recent runtime sessions |
| `runtime_logs` | Container stdout/stderr |
| `runtime_info` | Sandbox metadata |
| `runtime_health` | Liveness check |
| `runtime_exec` | Run a shell command inside the sandbox |

### Filesystem and network

| Tool | Purpose |
| --- | --- |
| `fs` | list, read, write, delete, move, copy, mkdir, stat, exists, chmod, symlink |
| `network` | list, expose, close sandbox ports |

### Usage and monitoring

| Tool | Purpose |
| --- | --- |
| `usage_quota` | Monthly runtime allowance, used and remaining |
| `runtime_monitoring` | CPU, memory, disk, uptime for a runtime |

### Artifacts

| Tool | Purpose |
| --- | --- |
| `artifact_list` | Artifacts from a build with SHA-256 and size |
| `artifact_verify` | Verify artifact integrity |

## Design notes

- The control plane is authoritative. The plugin never decides quota, lease or permission; it reports what the server says.
- Transport failures return an explanatory string to the AI rather than throwing, so the model can recover instead of aborting the session.
- The plugin maintains a WebSocket to the control plane for build and runtime events, with exponential backoff reconnection up to 10 attempts.
- Session state (known runtimes, builds) lives in `SessionState` so reconnects do not lose context.
- The ZIP writer is hand-rolled in `src/tools/project/zip.ts` because OpenCode loads plugins in a Bun runtime where optional native modules are unreliable. `tests/zip.test.ts` parses the produced bytes directly, so the archives are verified without shelling out to an external unzip.
- Tools return human-readable strings, since those become the AI's context.

## The build loop

```
project_upload  ->  build_submit  ->  build_status  ->  build_logs
                        |                              |
                        v                              v
                  GitHub Actions                 AI reads the failure
                  (3 min hard cap)               and fixes the project
```

`runtime_start` runs an already-built artifact. The server-agent never installs
dependencies or compiles source.
